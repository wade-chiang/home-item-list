## 01 · 專案

### 到期推算 → 提醒 → 換好了 → 重新推算

日常最常按的是「換好了」，其他都是想記才記：品牌型號、價格與採購單位、機身與耗材包裝的照片、改這次的週期與提前提醒天數、季節性的暫停、匯出備份。到期日是**推導值**，不存進資料庫。

- **已完成 P1、P2**：依位置分組的首頁與篩選、換好了、暫停、照片、價格、實際間隔回饋、匯出與還原、配色
- **接下來 P3**：Capacitor 包成 Android app、資料搬到手機、本地通知（原型已確認）
- **之後 P4**：拍耗材包裝自動填品牌型號、成本統計

> **講者備註**：這頁切到 demo 操作一輪「新增物品 → 換好了」。

## 02 · 產品

### 主要功能

- **首頁**：依位置分組，一眼看出哪些逾期、哪些快到期；上方三個數量方塊可以篩選
- **換好了**：一鍵記錄，順手記品牌型號、價格、耗材包裝照片
- **物品詳情**：更換歷史、目前型號與週期、物品照片
- **暫停**：冬天不開的冷氣先暫停，到指定日期自動恢復
- **設定**：位置與類別（icon、排序）、外觀與配色、提前提醒天數
- **備份**：匯出 zip、還原；伺服器每天自動備份

## 03 · 產品

### 幾個巧思

1. **不用自己取名**：顯示名稱由「位置 ＋ 類別 ＋ 補充名稱」組成，例如「主臥 · 冷氣濾網」。同位置同類別出現第二個時，才自動展開補充名稱欄位並提示
2. **不知道上次什麼時候換**：改問「下次大概什麼時候要換」，一樣建立第一筆紀錄，到期日照算，不會卡在必填欄位
3. **換了不同型號會標出來**：歷史上標「型號變更」「週期 90 → 60」。比較前先整理字串，3M 和 ３Ｍ 不會被當成兩種
4. **逾期的位置暫時置頂**：首頁的篩選離開就清除，避免停在「正常」時把逾期的東西藏起來
5. **幾乎每個動作都能復原**：刪物品、刪照片、改日期都有提示條與「復原」；刪照片前會先把原圖下載下來，復原時再傳回去

> **講者備註**：其他沒放上來的：實際間隔只提示不自動改（近三次平均與目前週期差 10 天以上才跳）、暫停一定要填恢復日、採購與更換分開記（一捲濾網換五台冷氣）、照片上傳前壓到長邊 1600 轉 JPEG、「拍耗材包裝」放在表單最上面（拆封時手上正拿著包裝）。

## 04 · 選擇的原則

### 後端終將消失，所以寫最少的鷹架

P1、P2 是網頁版：React 前端 ＋ PocketBase，Docker 跑在家裡的機器。P3 之後資料搬進手機，**後端整個不見**。

1. **過渡期的東西不值得雕**：網頁版的後端只是過渡，「寫最少的鷹架」比「後端寫得漂亮」重要
2. **暫定的選擇要有退場保險**：資料存取集中在 `src/repo/`，UI 不碰後端。換資料層時 UI 一行不改
3. **查證再選**：版本相容性、維護狀態、授權都查過，並記下查證日期；舊結論被推翻就更新文件
4. **每個依賴都要理由**：Claude 提理由與版本，我確認後才裝；0.x 的套件集中在單一檔案使用

## 05 · 選型

### 為什麼選 PocketBase

- **一個執行檔就是後端**：SQLite、REST API、檔案上傳、照片縮圖、管理後台、排程備份都內建
- **後端程式碼接近零**：不用寫 API、上傳、縮圖，schema 用 migration 定義

| 評估過的其他做法 | 結論 |
|---|---|
| 自建 Hono ＋ Prisma ＋ SQLite | 寫得漂亮但鷹架多；列為 PocketBase 的**退場方案** |
| P1 就直接做 app，跳過後端 | 省掉 Docker 與日後搬遷，但 P1 就要架 Android 環境、沒有後台與縮圖。想最快開始用，所以沒選 |
| P3 把 PocketBase 包進 app | 官方不支援，唯一的社群專案停在 v0.24.4，還要自己寫原生包裝。不划算 |

> **講者備註**：三個結論分別在 2026-09-11 查證過，理由寫在 CLAUDE.md 的決策紀錄。

## 06 · 選型

### 「先用用看」的選擇，要管理才不會拖著不換

PocketBase 還沒到 1.0，官方自己說不建議用在關鍵的正式環境。所以它從一開始就是**暫定**的，配了三件事，避免變成「不太滿意但也懶得換」。

1. **先寫下換掉它的條件**：權限擋住想做的事／資料庫與手寫型別對不上而反覆出 bug／升級遇到破壞性改版／需要的查詢做不到，被迫自己寫伺服器程式。出現任一項就重新評估，不靠模糊的不爽
2. **定期檢查，不是等出事**：P1、P2 結束各檢核一次，逐條對照並把結論寫進文件。**兩次都是四項全沒觸發**，所以續用；去留最後在 P3 決定
3. **同時準備好退路**：資料存取集中在 `src/repo/`，版本 pin 死、schema 進 git、資料進出用 zod 驗證。真要換，重寫的只有那一層，畫面不用動

- **當初選它的三個理由，兌現了兩個**：檔案上傳、照片縮圖不用自己寫
- **落空的是備份**：它的備份功能要管理員登入，前端用不了 → 改成 app 自己的備份格式，P3 搬到手機也能沿用
- **升級實測過一次**：v0.40.3 → v0.40.4，只改版本與 checksum，程式不用動

## 07 · 選型

### 其他選擇：選了什麼、沒選什麼

| 領域 | 選了 | 沒選 | 理由 |
|---|---|---|---|
| 前端 | Vite ＋ React | Next.js | 用不到 SSR、SEO；Capacitor 只吃靜態檔 |
| App 化 | Capacitor | React Native、Flutter | 表單＋清單＋相機＋通知都在舒適區；RN 要重寫 UI，Flutter 連資料層都要重寫 |
| 資料庫 | SQLite | Postgres | 單人沒有併發問題；備份就是複製一個資料夾 |
| 提醒 | 本地通知 | Telegram、Web Push | 不需要 HTTPS、伺服器、憑證 |
| Lint | oxlint | ESLint | 專案用 TypeScript 7，typescript-eslint 只支援 6.1 以前 |
| 拖曳 | `@dnd-kit/react` | `@dnd-kit/core` | 舊版停更；新版支援 React 19，代價是 0.x |
| 備份 | 自己的 zip 格式 | PocketBase 備份 API | API 要管理員登入；它的備份檔 P3 讀不了 |
| 日期欄位 | 文字＋格式檢查 | `date` 型別 | 後台改日期會用瀏覽器時區，悄悄差一天 |
| 照片 | JPEG | WebP | PocketBase 的縮圖只完整支援 jpg、png、gif |
| 字型 | 放進 repo | Google Fonts CDN | app 離線時載不到 |

> **講者備註**：「沒選」欄只列真的評估過的選項，不是硬湊。
>
> **Capacitor 而不是 React Native：**RN 是 React 但不是 DOM——div、span、button 要換成 View、Text、Pressable，Tailwind 要換 NativeWind，底部面板、選照片、壓縮照片、日期輸入、路由、localStorage、icon 套件全部要換，約 8,300 行畫面幾乎重寫；留得住的只有 shared、repo、backup 與測試。RN 換來的原生手感，在「幾十筆清單 ＋ 表單」的 app 上感覺不出來。Capacitor 的代價是畫面跑在 WebView，手感就是網頁手感，原生功能要靠外掛。（NativeWind 對 Tailwind v4 的支援度沒查證）

## 09 · 工作流程

### 文件就是記憶

session 會結束，長對話會被壓縮成摘要。**沒寫進文件的決定，下一個 session 就不存在**，甚至會被重新推翻。

| 文件 | 放什麼 |
|---|---|
| 全域 CLAUDE.md | 怎麼跟我合作：提案規則、破壞性操作、查證與標明未驗證的標準 |
| 專案 CLAUDE.md | 紀律、已知的坑、決策紀錄、指令。每條附「為什麼」 |
| PRODUCT.md | 規格：原型呈現不出來的規則與理由 |
| prototype/ | 確認過的畫面（P0、P3） |
| TASKS.md | 一次做一項，每項有完成定義，另有檢核點 |

- 推導出決定、發現文件有誤，**當下就提案寫入**，包含放哪一節、確切措辭
- 提案是義務，**寫不寫由我決定**
- 推翻文件裡的斷言時，**修正要跟更正一起提出**

### 分工，以及環境限制怎麼形成做法

| Claude | 我 |
|---|---|
| 寫程式與文件、跑測試與檢查 | 做決定、確認提案 |

- **沙箱**：Claude 的指令跑在沙箱裡，不能執行 docker → docker 由我跑，輸出貼回去

- **context 壓縮**：摘要後細節可能失真 → 以文件為準，不確定就回頭讀檔

## 11 · 工作流程

### 為什麼這個專案幾乎不派 sub agent

Claude Code 可以開出多個 sub agent 平行做事。這個專案刻意不這樣做，因為它解決不了這裡真正的瓶頸。

- **卡點是「要不要做」，不是「做得多快」**：流程是先提案、等我回覆選項。sub agent 不能替我做決定，派出去只會提早動手
- **回報一律當成未驗證**：重要的結論還是要自己再讀一次原始碼或 log，省不下來，還多一層轉述失真
- **剛寫進 CLAUDE.md 的規則傳不到**：CLAUDE.md 是 session 啟動時的快照，改完要重開 session 才會帶給 sub agent（2026-09-08 實測）。剛定下的規矩，它看不到
- **真正的瓶頸在實機驗證**：一次做一項、我在手機上測過才往下走，平行做沒有意義

**什麼時候適合**：大範圍的唯讀搜尋，例如「這個東西在哪些檔案被用到」——結論單純、容易自己驗證，也不會改到東西。

> **講者備註**：這頁的四個理由是現在整理出來的，不是逐字引用先前的對話；前面幾輪的內容已經被壓縮，我沒辦法原文核對。

## 12 · 品質

### 查證、原型關卡、實機驗證

- **查證，不靠猜**：讀 PocketBase 原始碼確認欄位空值、權限預設、刪除時怎麼清檔；查 npm registry 確認版本與相依；沒驗證的判斷要標明
- **原型關卡**：每階段開工前，畫面先做成 HTML 原型並確認。原型改一次便宜，寫進程式再改貴好幾倍
- **交付前**：test、lint、format、build 全過，再加手機實測

手機實測抓到、單元測試抓不到的：網頁版開相機拍照會遺失、底部面板開著時提示條按不到。
原型驗證不了的：相機、通知樣式、拖曳手感 → 留到實機測。

## 13 · 誠實

### Claude 判斷錯的時候

| 案例 | 怎麼發現 | 怎麼處理 |
|---|---|---|
| 規格寫「網頁版可以開相機拍照」 | 手機實測照片遺失 | 更正規格，P2 改成只能從相簿選，拍照留到 P3 |
| 估「很多年才會到 49 筆更換紀錄」 | 重新估算時發現沒考慮 7 天週期 | 上限調到 1000，實測 999 筆 |
| 把舊的指令輸出當成現況在推原因 | 事後對照輸出的時間 | 更正推論；規則加上「先確認輸出的來源和時間」 |
| 還原備份時照片被背景清掉 | 升級後發現照片不見，查出是更早一次還原造成 | 查請求紀錄與原始碼找原因、修正、四種情況實測，寫進 CLAUDE.md |

- **對策都寫成規則**：沒驗證的要標明、判斷錯要明講、估算先列假設、推翻斷言時要一起提修正
