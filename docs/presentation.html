03產品

幾個巧思

  • 不用自己取名：顯示名稱由「位置 ＋ 類別 ＋ 補充名稱」組成，例如「主臥 · 冷氣濾網」。同位置同類別出現第二個時，才自動展開補充名稱欄位並提示
  • 不知道上次什麼時候換：改問「下次大概什麼時候要換」，一樣建立第一筆紀錄，到期日照算，不會卡在必填欄位
  • 換了不同型號會標出來：歷史上標「型號變更」「週期 90 → 60」。比較前先整理字串，3M 和 ３Ｍ 不會被當成兩種
  • 逾期的位置暫時置頂：首頁的篩選離開就清除，避免停在「正常」時把逾期的東西藏起來
  • 幾乎每個動作都能復原：刪物品、刪照片、改日期都有提示條與「復原」；刪照片前會先把原圖下載下來，復原時再傳回去

講者備註：其他沒放上來的：實際間隔只提示不自動改（近三次平均與目前週期差 10 天以上才跳）、暫停一定要填恢復日、採購與更換分開記（一捲濾網換五台冷氣）、照片上傳前壓到長邊 1600 轉 JPEG、「拍耗材包裝」放在表單最上面（拆封時手上正拿著包裝）。

04選擇的原則

後端終將消失，所以寫最少的鷹架

P1、P2 是網頁版：React 前端 ＋ PocketBase，Docker 跑在家裡的機器。 P3 之後資料搬進手機，後端整個不見。

1 · 過渡期的東西不值得雕

網頁版的後端只是過渡，「寫最少的鷹架」比「後端寫得漂亮」重要

2 · 暫定的選擇要有退場保險

資料存取集中在 src/repo/，UI 不碰後端。換資料層時 UI 一行不改

3 · 查證再選

版本相容性、維護狀態、授權都查過，並記下查證日期；舊結論被推翻就更新文件

4 · 每個依賴都要理由

Claude 提理由與版本，我確認後才裝；0.x 的套件集中在單一檔案使用

05選型

為什麼選 PocketBase

  • 一個執行檔就是後端：SQLite、REST API、檔案上傳、照片縮圖、管理後台、排程備份都內建
  • 後端程式碼接近零：不用寫 API、上傳、縮圖，schema 用 migration 定義
評估過的其他做法結論
自建 Hono ＋ Prisma ＋ SQLite寫得漂亮但鷹架多；列為 PocketBase 的退場方案
P1 就直接做 app，跳過後端省掉 Docker 與日後搬遷，但 P1 就要架 Android 環境、沒有後台與縮圖。想最快開始用，所以沒選
P3 把 PocketBase 包進 app官方不支援，唯一的社群專案停在 v0.24.4，還要自己寫原生包裝。不划算

講者備註：三個結論分別在 2026-09-11 查證過，理由寫在 CLAUDE.md 的決策紀錄。

06選型

「先用用看」的選擇，要管理才不會拖著不換

PocketBase 還沒到 1.0，官方自己說不建議用在關鍵的正式環境。 所以它從一開始就是暫定的，配了三件事，避免變成「不太滿意但也懶得換」。

1 · 先寫下換掉它的條件

權限擋住想做的事／資料庫與手寫型別對不上而反覆出 bug／升級遇到破壞性改版／需要的查詢做不到，被迫自己寫伺服器程式。出現任一項就重新評估，不靠模糊的不爽

2 · 定期檢查，不是等出事

P1、P2 結束各檢核一次，逐條對照並把結論寫進文件。兩次都是四項全沒觸發，所以續用；去留最後在 P3 決定

3 · 同時準備好退路

資料存取集中在 src/repo/，版本 pin 死、schema 進 git、資料進出用 zod 驗證。真要換，重寫的只有那一層，畫面不用動

  • 當初選它的三個理由，兌現了兩個：檔案上傳、照片縮圖不用自己寫
  • 落空的是備份：它的備份功能要管理員登入，前端用不了 → 改成 app 自己的備份格式，P3 搬到手機也能沿用
  • 升級實測過一次：v0.40.3 → v0.40.4，只改版本與 checksum，程式不用動

11工作流程

為什麼這個專案幾乎不派 sub agent

Claude Code 可以開出多個 sub agent 平行做事。這個專案刻意不這樣做，因為它解決不了這裡真正的瓶頸。

  • 卡點是「要不要做」，不是「做得多快」：流程是先提案、等我回覆選項。sub agent 不能替我做決定，派出去只會提早動手
  • 回報一律當成未驗證：重要的結論還是要自己再讀一次原始碼或 log，省不下來，還多一層轉述失真
  • 剛寫進 CLAUDE.md 的規則傳不到：CLAUDE.md 是 session 啟動時的快照，改完要重開 session 才會帶給 sub agent（2026-09-08 實測）。剛定下的規矩，它看不到
  • 真正的瓶頸在實機驗證：一次做一項、我在手機上測過才往下走，平行做沒有意義

什麼時候適合

大範圍的唯讀搜尋，例如「這個東西在哪些檔案被用到」——結論單純、容易自己驗證，也不會改到東西。

講者備註：這頁的四個理由是現在整理出來的，不是逐字引用先前的對話；前面幾輪的內容已經被壓縮，我沒辦法原文核對。

12品質

查證、原型關卡、實機驗證

查證，不靠猜

讀 PocketBase 原始碼確認欄位空值、權限預設、刪除時怎麼清檔；查 npm registry 確認版本與相依；沒驗證的判斷要標明

原型關卡

每階段開工前，畫面先做成 HTML 原型並確認。原型改一次便宜，寫進程式再改貴好幾倍

交付前

test、lint、format、build 全過，再加手機實測

  • 手機實測抓到、單元測試抓不到的：網頁版開相機拍照會遺失、底部面板開著時提示條按不到
  • 原型驗證不了的：相機、通知樣式、拖曳手感 → 留到實機測
